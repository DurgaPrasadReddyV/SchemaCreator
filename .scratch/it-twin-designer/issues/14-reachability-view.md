# 14 — Reachability view `/reachability` (the defining feature)

**What to build:** The reachability simulation at `/reachability`, wiring the pure engine (ticket 10) to the graph (ticket 12). A query root picker re-filtered by mode + a `Segmented` control ("Who can reach this" = data→user / "What this can reach" = user→data) that also re-filters the root picker; `Public`/`Unclassified`/untagged fields are never offered as data→who roots. Running the query computes reachability and animates the reachable subgraph hop-by-hop: reachable nodes lit (full opacity, thicker stroke), unreachable dimmed (~0.14 opacity), root ringed in amber, active edges showing SVG `<animateMotion>` "packets" gated to the active hop (NOT `animated: true` `stroke-dasharray` marching ants — that is a CPU hog at scale). Per-hop reveal ordering is driven by the BFS `perHopReachable` buckets so the animation reveals exactly what the engine computed, in order. The descendant-flood step is made legible: a flood-reached step is annotated "accesses (flood via Customer)" with the contains-path highlighted in a second accent color. Layout: graph stage + a right side panel (Query → Hop table → Objects table → Inspector stacked) + a slim bottom playback bar (Reset / Step ◀ / Play / Step ▶ / scrubber + hop count) with ←/→/space keyboard. The hop table: one row per reachable node (Hop, Object, Reached-via relation + direction, Classification, Capabilities), sorted by hop, click-syncs graph + inspector; the inspector shows the full access chain for a reached node; the hop table's direction follows the mode `Segmented`. A `requestAnimationFrame`/`setTimeout` ticker in the view (not the engine) advances `currentHop`. The reachability highlight color is aqua, distinct from the blue classification ramp. Scale mitigations: memoize nodes/edges, contextual zoom, no heavy CSS/filter/blur on nodes, edge labels on hover/highlight only; keep `reachableIds`/`selectedIds` in a separate store slice, never filter `nodes` inside children.
